Modern Fortran SQP OPTimizer

SQPOPT

A modular, extensible Sequential Quadratic Programming solver for large-scale, sparse, nonlinearly constrained optimization problems.

Get started Options reference API docs Tags

SQPOPT solves problems of the form

\[ \begin{aligned} \min_{x}\quad & f(x) \\ \text{subject to}\quad & c_{lb} \le c(x) \le c_{ub} && \text{(nonlinear, possibly two-sided, constraints)}\\ & x_{lb} \le x \le x_{ub} && \text{(variable bounds)} \end{aligned} \]

where an equality constraint is written as c_lb(i) = c_ub(i). The objective, the constraints, and their first derivatives are supplied as callbacks. The constraint Jacobian is stored in sparse coordinate (COO) format, and the Hessian of the Lagrangian is approximated by a matrix-free, limited-memory quasi-Newton operator, or supplied exactly by the user, also in sparse form. No dense n×n or m×n array is ever formed, so the library scales to large, sparse problems.

SQP method

Nonlinear objective, nonlinear equality and inequality constraints, and bounds.

Sparse throughout

COO constraint Jacobian, matrix-free L-BFGS / L-SR1 Hessian, sparse LU-based QP solver.

Modular

Problem, options, Hessian, QP solver, line search and convergence are separate modules you can swap independently.

Robust globalization

Filter line search (default), funnel, Armijo, watchdog, or exact line search, or a trust region; second-order corrections.

Selectable precision

Single, double, or quadruple precision reals.

FPM-native

Add it to any project as a Fortran Package Manager dependency.

Work in progress. The API is still evolving. The API reference generated by FORD from the source code always matches the current code.
Python interface. SQPOPT can also be called from Python, through a minimize function modeled on scipy.optimize.minimize. See Python. The Python interface is also a work in progress, and may change.

Installation

SQPOPT is built with the Fortran Package Manager. To use it in your own project, add it to your fpm.toml:

[dependencies]
sqpopt = { git = "https://github.com/jacobwilliams/sqpopt" }

FPM fetches and builds its dependencies for you. SQPOPT uses double precision (real64) unless you choose another kind with a preprocessor flag:

fpm build --profile release --flag "-DREAL32"    # single precision
fpm build --profile release --flag "-DREAL128"   # quadruple precision

The working kind is exported as sqpopt_module_wp from sqpopt_kinds. The examples below import it as wp.

Large problems and the stack. Some compilers and flags put local arrays whose size is only known at run time, and the temporary arrays of expressions, on the stack: gfortran with -fstack-arrays (which -Ofast turns on), and the Intel compilers unless -heap-arrays is given. A large problem then overflows the stack (usually 8 MB), and the program crashes without a message. The library doesn't depend on this: every array of its own whose size grows with the problem is allocated on the heap. Built with gfortran's -fstack-arrays, it solves problems with a million variables in an 8 MB stack. Two things are not covered:

  • the dense QP solver (sqpopt_qp_dense), which is meant for small problems and works with dense temporary matrices: with such flags, use it for a few hundred variables at most;
  • your own code. An array sized by the problem that is a local variable of the program or of fc/gjac, or an array expression given as an argument (spread(...), an array constructor), is placed as your compiler decides. Make such arrays allocatable, or raise the stack limit (ulimit -s, and OMP_STACKSIZE for the threads of an OpenMP program).

Three options, meant for large problems, use sparse factorizations: inertia control, the direct QP method, and direct least squares. Their sparse solver is options%linear_solver (see Sparse solver): QDLDL, which FPM fetches, so it is always available, or the MUMPS solver, which is optional, because FPM can't fetch it. To build with MUMPS, define HAS_MUMPS, put MUMPS's dmumps_struc.h on the include path, and link with its sequential, double precision library. With conda-forge's mumps-seq package:

fpm build --profile release --flag "-DHAS_MUMPS -I$CONDA_PREFIX/include" --link-flag "-ldmumps_seq"

The constant sqpopt_has_mumps (from sqpopt_symmetric_solver_module) says whether the library was built this way. Without it, everything works as usual, the three options use QDLDL, and only linear_solver = sqpopt_linear_solver_mumps is reported as invalid input. A build with MUMPS must use double precision (the default): REAL32 and REAL128 don't compile with it. Your own program must be linked with -ldmumps_seq too.

The dense solver can also use LAPACK (linear_solver = sqpopt_linear_solver_lapack, see Sparse solver). That is optional too: define HAS_LAPACK and link with LAPACK and BLAS (fpm build --flag "-DHAS_LAPACK" --link-flag "-llapack -lblas"; the pixi environment has them, with the tasks build-lapack, test-lapack, and run-lapack). sqpopt_has_lapack says whether the library was built this way; it also needs double precision, and both directives can be used together.

Quick start

You need three objects: a problem (sizes, bounds, sparsity, and callbacks), some options, and the solver.

use sqpopt_module,         only: sqpopt_type
use sqpopt_problem_module, only: sqpopt_problem_type
use sqpopt_options_module, only: sqpopt_options_type
use sqpopt_kinds,          only: wp => sqpopt_module_wp

type(sqpopt_type)         :: solver
type(sqpopt_problem_type) :: problem
type(sqpopt_options_type) :: options
real(wp) :: x(n), lambda(m)
integer  :: istat

call problem%set_problem_size(n, m)
call problem%set_bounds(x_lb, x_ub, c_lb, c_ub)
call problem%set_jacobian_sparsity(nnz, irow, icol)          ! fixed sparsity pattern
call problem%set_functions(fc=fc, gjac=gjac)                 ! optionally also data=...

call solver%initialize(problem=problem, options=options)
call solver%solve(x0, istat)            ! optionally also lambda0=...
call solver%get_solution(x, lambda)     ! optionally also z (bound multipliers)
print *, solver%status_message()        ! e.g. 'converged successfully'

Before iterating, solve checks the problem definition and every option. If anything is wrong it returns istat = sqpopt_invalid_input, and status_message() gives the reason. It also moves x0 inside the variable bounds, so your functions are never evaluated outside the bounds.

Every call to solve starts from the configuration given to initialize. No state (penalty parameter, filter, Hessian, …) carries over from a previous solve.

User functions

The problem is defined by two routines: fc evaluates the objective \( f(x) \) and the constraints \( c(x) \) together, and gjac evaluates the objective gradient and the constraint Jacobian together. (They usually share intermediate results, which each routine can compute once.)

subroutine fc(x, f, c, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp),               intent(out)   :: f
    real(wp), dimension(:), intent(out)   :: c        ! dimension(m); m may be 0
    integer,                intent(inout) :: status   ! 0 on entry
    class(*), optional,     intent(inout) :: data
    f = ...
    c = ...
end subroutine fc

subroutine gjac(x, g, jac_val, accuracy, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp), dimension(:), intent(out)   :: g        ! dimension(n)
    real(wp), dimension(:), intent(out)   :: jac_val  ! dimension(nnz); nnz may be 0
    integer,                intent(in)    :: accuracy ! sqpopt_derivatives_fast or _accurate
    integer,                intent(inout) :: status   ! 0 on entry
    class(*), optional,     intent(inout) :: data
    g = ...
    jac_val = ...
end subroutine gjac

The Jacobian values must be in the order of the irow/icol pattern given to set_jacobian_sparsity. The solver keeps a small cache of recent evaluations, so asking for c at a point where it just evaluated f (or for the Jacobian where it just evaluated the gradient) doesn't call your routine again.

accuracy
The accuracy the solver asks for: sqpopt_derivatives_accurate, or, with options%derivative_accuracy = sqpopt_derivatives_fast, sqpopt_derivatives_fast while it is far from a solution (see Fast derivatives). With analytic derivatives, ignore it.
status
Leave it 0 on success. Set it > 0 if the function can't be evaluated at x (for example, a domain error). The solver treats that point like one where the function returned NaN (all of its outputs, e.g. both f and c), and backs off from it. Set it < 0 to stop the solver (sqpopt_user_requested_stop). No user function is called again after that.
data
The object passed as set_functions(..., data=my_data) (absent if none was given). Use it to pass any context to the functions without module variables, and access it with select type. It is pointed to, not copied, so the caller's object needs the target attribute, and any changes the functions make to it are seen by the caller. It is also passed to the report callback.

Fast derivatives (optional)

If your derivatives are approximations whose accuracy has a cost (finite differences, most often: a forward difference costs \( n \) function evaluations, a central one \( 2n \) and is far more accurate), set options%derivative_accuracy = sqpopt_derivatives_fast. Then the solver asks gjac for fast derivatives (accuracy = sqpopt_derivatives_fast) far from a solution, where rough derivatives give about as good a step, and switches to accurate ones (sqpopt_derivatives_accurate) for the rest of the solve (as SNOPT switches from forward to central differences). It switches as soon as either of these holds:

  • it is near a solution: the KKT and feasibility errors are below derivative_switch_tol;
  • it would stop at this point (converged, acceptable, stalled, or infeasible): the gradient and Jacobian are re-evaluated accurately and the tests redone, so it never stops on the strength of fast derivatives;
  • progress stalls, or a step fails: both can be caused by derivatives that are too rough.

Because of the last two rules, derivative_switch_tol is only a shortcut, and a small one works best: on the Hock–Schittkowski problems with finite-difference derivatives for all of them, switching from forward to central differences took about 40% fewer function evaluations than central differences throughout, and solved the same problems, for any derivative_switch_tol from \( 10^{-5} \) (the default, \( 10 \times \) ktol) down; switching earlier (\( 10^{-3} \)) saved only 9%. Forward differences throughout were cheaper still, but failed on 2 problems. The iteration of the switch is in results%derivative_switch_iteration, and flagged D in the log.

subroutine gjac(x, g, jac_val, accuracy, status, data)
    ...
    if (accuracy == sqpopt_derivatives_fast) then
        ! forward differences of fc
    else
        ! central differences of fc
    end if
end subroutine gjac

Exact Hessian (optional)

With options%hessian_mode = sqpopt_hessian_exact, the solver uses your Hessian of the Lagrangian instead of a quasi-Newton approximation. Supply a third routine, hess, and its fixed sparsity pattern:

subroutine hess(x, lambda, hess_val, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp), dimension(:), intent(in)    :: lambda    ! dimension(m): the constraint multipliers
    real(wp), dimension(:), intent(out)   :: hess_val  ! dimension(hess_nnz)
    integer,                intent(inout) :: status    ! 0 on entry
    class(*), optional,     intent(inout) :: data
    hess_val = ...  ! the nonzeros of  grad^2 f(x) - sum_i lambda(i) * grad^2 c_i(x)
end subroutine hess

call problem%set_hessian_sparsity(hess_nnz, hrow, hcol)
call problem%set_functions(fc, gjac, hess=hess)
options%hessian_mode = sqpopt_hessian_exact

Give each off-diagonal element only once, in either triangle (for example, the lower triangle): an entry \( (i,j) \), \( i\ne j \), stands for both \( (i,j) \) and \( (j,i) \). The values must be in the order of the pattern. hess is called once per major iteration, with the current multipliers (for the original, unscaled problem). The Hessian may be indefinite: when the QP subproblem finds negative curvature, fails, or doesn't give a descent direction, the solver re-solves it with the Hessian shifted by a multiple of the identity, increasing the shift as needed (see Hessian). In a build with MUMPS, options%inertia_control finds the shift from a factorization instead (see Inertia control), and options%direct_qp solves the QP subproblems with it (see Direct method), which is much faster on large problems.

Progress callback

Pass report=my_report to initialize to be called once per major iteration. Set user_stop = .true. to stop after the current iteration. All values are for the original (unscaled) problem.

subroutine my_report(iter, x, f, c, lambda, user_stop, data)
    integer,                intent(in)    :: iter       ! major iteration (starts at 1)
    real(wp), dimension(:), intent(in)    :: x, c, lambda
    real(wp),               intent(in)    :: f
    logical,                intent(out)   :: user_stop
    class(*), optional,     intent(inout) :: data
    user_stop = .false.
end subroutine my_report

Worked example: Hock–Schittkowski 71

\[ \begin{aligned} \min_{x}\quad & x_1 x_4 (x_1 + x_2 + x_3) + x_3 \\ \text{subject to}\quad & x_1^2 + x_2^2 + x_3^2 + x_4^2 = 40 \\ & x_1 x_2 x_3 x_4 \ge 25 \\ & 1 \le x_i \le 5 \end{aligned} \]

Starting from \( x_0 = (1, 5, 5, 1) \), the solution is \( x^* \approx (1,\ 4.743,\ 3.821,\ 1.379) \) with \( f^* \approx 17.014 \). Both constraints are active there.

program hs71

use sqpopt_module,         only: sqpopt_type
use sqpopt_problem_module, only: sqpopt_problem_type
use sqpopt_options_module, only: sqpopt_options_type
use sqpopt_kinds,          only: wp => sqpopt_module_wp

implicit none

real(wp), parameter :: big = 1.0e20_wp  !! "no bound"
type(sqpopt_type)         :: solver
type(sqpopt_problem_type) :: problem
type(sqpopt_options_type) :: options
real(wp) :: x(4), lambda(2)
integer  :: istat

! equality constraint (index 1) first, then the inequality (index 2)
call problem%set_problem_size(n=4, m=2)
call problem%set_bounds(x_lb=[1.0_wp,1.0_wp,1.0_wp,1.0_wp], &
                        x_ub=[5.0_wp,5.0_wp,5.0_wp,5.0_wp], &
                        c_lb=[40.0_wp, 25.0_wp], c_ub=[40.0_wp, big])
call problem%set_jacobian_sparsity(nnz=8, irow=[1,1,1,1,2,2,2,2], &
                                          icol=[1,2,3,4,1,2,3,4])
call problem%set_functions(fc=fc, gjac=gjac)

options%print_level = 1 ! set verbosity level

call solver%initialize(problem=problem, options=options)
call solver%solve([1.0_wp, 5.0_wp, 5.0_wp, 1.0_wp], istat)
call solver%get_solution(x, lambda)
print *, solver%status_message()
print *, 'x = ', x

contains

    subroutine fc(x, f, c, status, data)
    !! evaluate the objective and constraints at the current point `x`
    real(wp), dimension(:), intent(in)    :: x !! current point `dimension(n)`
    real(wp),               intent(out)   :: f !! objective value at `x`
    real(wp), dimension(:), intent(out)   :: c !! constraint values at `x`
    integer,                intent(inout) :: status !! status flag (input/output)
    class(*), optional,     intent(inout) :: data !! user-provided data (optional)
    f = x(1)*x(4)*(x(1)+x(2)+x(3)) + x(3)
    c = [sum(x**2), product(x)]
    end subroutine fc

    subroutine gjac(x, g, jac_val, accuracy, status, data)
    !! evaluate the gradient of the objective and the Jacobian of the constraints at the current point `x`
    real(wp), dimension(:), intent(in)    :: x !! current point `dimension(n)`
    real(wp), dimension(:), intent(out)   :: g !! gradient of the objective at `x`
    real(wp), dimension(:), intent(out)   :: jac_val !! nonzero entries of the Jacobian at `x`
    integer,                intent(in)    :: accuracy !! requested accuracy: `sqpopt_derivatives_fast` or `sqpopt_derivatives_accurate`
    integer,                intent(inout) :: status !! status flag (input/output)
    class(*), optional,     intent(inout) :: data !! user-provided data (optional)
    g = [x(4)*(2.0_wp*x(1)+x(2)+x(3)), x(1)*x(4), x(1)*x(4) + &
         1.0_wp, x(1)*(x(1)+x(2)+x(3))]
    jac_val(1:4) = 2.0_wp*x                           ! row 1: d(sum x^2)/dx
    jac_val(5:8) = [x(2)*x(3)*x(4), x(1)*x(3)*x(4), & ! row 2: d(prod x)/dx
                    x(1)*x(2)*x(4), x(1)*x(2)*x(3)]
    end subroutine gjac

end program hs71

For more complete examples, see test/test_basic.f90, test/test_hs71.f90 (which solves this problem eleven different ways), and test/test_medium.f90.

The derivative check of level 2 needs no evaluations. Between two consecutive iterates \( x \) and \( x^+ = x + s \), the change of a function is \( \tfrac12 (\nabla c(x) + \nabla c(x^+))^T s \) up to a term of the third order in \( s \), and the solver has the values and the derivatives at both points. A constraint (or the objective) whose changes differ from that by more than 20% in most of the steps has derivatives that don't match its values, or isn't smooth along the way. Only steps that change no variable by more than 10% of its size are used. On the 305 Hock–Schittkowski problems, whose derivatives are right, it suspects three: two whose objective is a root that isn't differentiable at the solution, and one whose derivatives are finite differences.

The history file. With diagnostic_level ≥ 2 and options%diagnostics_unit set to a unit that is open for formatted writing, one line per major iteration is written to it, as comma-separated values under a header line: iteration, objective, infeasibility, kkt_error, stationarity, alpha, step_norm, fc (calls so far), fc_iteration, qp_iterations, qp_status, largest_multiplier, globalization and hessian (the last two columns of the log at print_level = 2), working_set_changes, time, time_functions, time_qp, time_factorization (seconds, of that iteration), and flags. A field that doesn't apply is empty (the last line is the final point, from which no step was taken). The file is data for plotting, not part of the log, so it is written whatever print_level is.

Scaling

SQPOPT works best when the variables are of order 1 and of similar magnitude, and when the objective and each constraint change by comparable amounts for a unit change in the variables. It scales the objective and the constraints for you, but not the variables: choosing their units is up to you.

What is scaled automatically

With options%scaling (on by default), the objective and each constraint are scaled down at the starting point, so that no element of their gradients is larger than scaling_max_gradient (100); see Solver options. ktol and ctol then apply to the scaled problem, and all results are reported for the original one. The factors are computed once, at x0, and only ever scale down: a function with tiny gradients isn't scaled up. So that a poor starting point, where the objective is scaled far down, can't make ktol meaninglessly loose, the stationarity residual of the unscaled problem must also be below dual_inf_tol, as in IPOPT.

The factors come from one point, which may not represent the problem. If the gradient at x0 is many orders of magnitude larger than it is near the solution, the scaled problem's tolerances mean little in the original units, and the solver can stop, with sqpopt_acceptable, far from the solution. Two things limit that. No factor is smaller than scaling_min_value (\( 10^{-8} \)): the Zakharov function with 1,000 variables, whose gradient at its starting point is \( 3 \times 10^{19} \), stopped at an objective of \( 5 \times 10^{6} \) without that limit, and reaches \( 8 \times 10^{-7} \) with it (the minimum is 0). And if a solve ends with a large stationarity error (original problem) in its summary, turn the scaling off (options%scaling = .false.), scale the problem yourself, or start from a better point. Also, the solver doesn't stop at the acceptable level while the objective is still changing by more than acceptable_obj_change_tol per iteration. Schwefel's function 1.2 with 1,000 variables, whose starting gradient of \( 5 \times 10^{7} \) is within the limit on the factors, stopped at an objective of 593 before that test was added, and now stops at 0.56; without the scaling it reaches \( 10^{-17} \), in 7 iterations.

Why the size of the variables matters

Several parts of the algorithm assume that a unit change means much the same for every variable:

Scaling the variables yourself

Choose a typical magnitude \( d_j > 0 \) for each variable, and solve for \( y = x/d \) instead of \( x \). In the user functions, evaluate at \( x = d\,y \), and multiply the objective gradient and each column of the Jacobian by \( d \) (the chain rule, \( \partial f/\partial y_j = d_j\,\partial f/\partial x_j \)). The sparsity pattern doesn't change:

real(wp), dimension(n) :: d   ! typical magnitude of each variable (e.g. 1e6, 1e-3, 1, ...)

subroutine fc_y(y, f, c, status, data)   ! the problem in y = x/d
    real(wp), dimension(:), intent(in)    :: y
    real(wp),               intent(out)   :: f
    real(wp), dimension(:), intent(out)   :: c
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    call fc(d*y, f, c, status, data)
end subroutine fc_y

subroutine gjac_y(y, g, jac_val, accuracy, status, data)
    real(wp), dimension(:), intent(in)    :: y
    real(wp), dimension(:), intent(out)   :: g, jac_val
    integer,                intent(in)    :: accuracy
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    call gjac(d*y, g, jac_val, accuracy, status, data)
    ! (icol: the column indices of the Jacobian's sparsity pattern)
    g       = d*g                 ! df/dy_j   = d_j df/dx_j
    jac_val = d(icol)*jac_val     ! dc_i/dy_j = d_j dc_i/dx_j
end subroutine gjac_y

Then divide the variable bounds and the starting point by \( d \) (x_lb/d, x_ub/d, x0/d; leave infinite bounds as they are), solve, and map the results back: \( x = d\,y \). The objective, the constraint values, and their multipliers \( \lambda \) are unchanged, and the variable-bound multipliers are \( z_x = z_y/d \). With an exact Hessian, scale its elements too: \( H^y_{ij} = d_i\,d_j\,H^x_{ij} \).

Other things to check

  • Constraint units. The automatic scaling reduces large gradients but doesn't enlarge small ones. A constraint whose values are of order \( 10^{-6} \) is effectively ignored by ctol = 1e-8, so express it in larger units, or multiply it by a constant. (Its multiplier is then divided by the same constant.)
  • The starting point. The objective and constraint scale factors are computed there, and never updated. At a poor starting point where a gradient is huge, a function can be scaled far down, which makes the tolerances very loose in its original units. (dual_inf_tol limits that for the objective's stationarity test.)
  • Unscaled large variables. If you do solve with large variables, also enlarge trust_region%radius0 and radius_max (when using the trust region), and read ktol and xtol in your variables' units.

Least-squares problems sqpopt_nlls_type

Experimental. This interface is new and may change. It has been tested on few problems, and on plain fits it finds the best fit less often than a solver written for least squares (see What to expect below).

An optional interface, for problems whose objective is a sum of squares:

\[ \min_x \; \tfrac12 \sum_{i=1}^{l} r_i(x)^2 \quad \text{s.t.} \quad c_l \le c(x) \le c_u, \quad x_l \le x \le x_u \]

The \( r_i \) are the residuals: in a data-fitting problem, the differences between a model and the data. Use it for those, and for a system of equations that can't all hold (more equations than unknowns). Given to the solver as equality constraints, such a system makes every QP subproblem inconsistent, and the solve ends as sqpopt_infeasible at best, after many restoration steps.

How it works. The module sqpopt_nlls_module is a layer on top of the solver, which is not changed by it and has no least-squares mode of its own. It gives the solver the problem in the form Schittkowski proposed for his code DFNLP, with a new variable \( z_i \) for each residual:

\[ \min_{x,z} \; \tfrac12 z^T z \quad \text{s.t.} \quad r(x) - z = 0, \quad c_l \le c(x) \le c_u, \quad x_l \le x \le x_u \]

This is an ordinary nonlinear program in \( n + l \) variables and \( l + m \) constraints. Its QP subproblems are consistent as far as the residuals go (any step in \( x \) has a \( z \) to go with it), and their step is a Gauss-Newton step with a correction from the Hessian approximation, as in the codes written for least squares.

Fortran. You give the residuals and the constraints in one routine, and the nonzeros of their two Jacobians in another, as fc and gjac do for an ordinary problem (see User functions; status, accuracy, and data mean the same). This is example/nlls_bard.f90, which fits the model \( y = x_1 + u/(v x_2 + w x_3) \) to 15 points:

subroutine residuals(x, r, c, status, data)
    real(wp), dimension(:), intent(in)    :: x      ! variables
    real(wp), dimension(:), intent(out)   :: r      ! residuals
    real(wp), dimension(:), intent(out)   :: c      ! constraints (none here)
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    integer :: i
    do i = 1, l
        r(i) = y(i) - (x(1) + i/((16 - i)*x(2) + min(i, 16 - i)*x(3)))
    end do
end subroutine residuals

subroutine jacobian(x, rjac_val, cjac_val, accuracy, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp), dimension(:), intent(out)   :: rjac_val ! nonzeros of the residuals' Jacobian
    real(wp), dimension(:), intent(out)   :: cjac_val ! nonzeros of the constraints' Jacobian (none here)
    integer,                intent(in)    :: accuracy
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    integer :: i
    real(wp) :: d
    do i = 1, l
        d = ((16 - i)*x(2) + min(i, 16 - i)*x(3))**2
        rjac_val(3*i-2) = -1.0_wp
        rjac_val(3*i-1) = i*(16 - i)/d
        rjac_val(3*i)   = i*min(i, 16 - i)/d
    end do
end subroutine jacobian
use sqpopt_nlls_module, only: sqpopt_nlls_type

type(sqpopt_nlls_type) :: nlls

                     rjac_irow=irow, rjac_icol=icol, x_lb=[0.0_wp, 0.0_wp, 0.0_wp])
call nlls%solve([1.0_wp, 1.0_wp, 1.0_wp], istat)

solve returns the solver's status code: sqpopt_success at a least-squares solution, whether or not the residuals are zero there. get_solution returns the variables and, optionally, the residuals, the sum of their squares, and the multipliers of the constraints. get_results returns the solver's results, which are those of the transformed problem: x is the variables followed by \( z \), and c and lambda are those of the \( l \) residual equations followed by the constraints.

The Hessian. By default the solver approximates the Hessian of the transformed problem as it does any other (L-BFGS). With options%hessian_mode = sqpopt_hessian_exact, the module supplies the Gauss-Newton Hessian instead: the identity on \( z \) and zero on \( x \), which neglects the second derivatives of the residuals and of the constraints. The solver's Hessian shift then acts as the damping of the Levenberg–Marquardt method. It usually takes fewer iterations, mostly so when the residuals are small at the solution (6 against 18 on the example), but it fails more often.

Python. sqpopt.least_squares does the same on top of minimize:

import numpy as np
from sqpopt import least_squares

y = np.array([0.14, 0.18, 0.22, 0.25, 0.29, 0.32, 0.35, 0.39, 0.37, 0.58, 0.73, 0.96, 1.34, 2.10, 4.39])
u = np.arange(1, 16.0); v = 16 - u; w = np.minimum(u, v)

def residuals(x):
    return y - (x[0] + u/(v*x[1] + w*x[2]))

def jacobian(x):
    d = (v*x[1] + w*x[2])**2
    return np.column_stack([-np.ones(15), u*v/d, u*w/d])

res = least_squares(residuals, [1, 1, 1], jacobian, bounds=[(0, None)] * 3)
print(res.x, res.cost, res.message)

Its bounds, constraints, options, max_step, and output files are those of minimize (see Python), jac_sparsity gives the pattern of a sparse Jacobian, and gauss_newton=True selects the Gauss-Newton Hessian (as a dense matrix in Python, so for small problems). The result has x, fun (the residuals), cost (half the sum of their squares), the multipliers, and nlp, the result of minimize for the transformed problem.

What to expect. For a fit with no constraints other than bounds, a solver written for least squares (scipy's least_squares, MINPACK's lmder) is the better choice. Use this interface when the fit also has general constraints, which those solvers don't take, or when the equations would otherwise be given to SQPOPT as equality constraints.

The numbers behind that: 94 test problems from CUTEst, each a system with more equations than unknowns and no other constraints, solved four ways with at most 250 iterations. A method counts as having found the best fit on a problem if its sum of squares is as small as the smallest that any of the four reached.

Limits. The QP subproblem has \( n + l \) variables (DFNLP eliminates \( z \) from it, SQPOPT doesn't), so with many residuals the sparse QP solver is the one to use, which sqpopt_qp_auto chooses by the problem's size. Only the sum of squares is offered: the same device gives the \( l_1 \) and maximum norms, which are not implemented.

Python

The python/sqpopt package calls the solver from Python, with an interface like scipy.optimize.minimize. Its native extension is built with NumPy's f2py. Build it with pixi run build-python.

import numpy as np
from sqpopt import minimize, NonlinearConstraint

# HS71 (see the worked example):
def f(x):
    return x[0]*x[3]*(x[0]+x[1]+x[2]) + x[2]

def grad(x):
    return [x[3]*(2*x[0]+x[1]+x[2]), x[0]*x[3], x[0]*x[3] + 1, x[0]*(x[0]+x[1]+x[2])]

def cons(x):
    return [np.sum(x**2), np.prod(x)]

def cons_jac(x):
    return [2*x, [x[1]*x[2]*x[3], x[0]*x[2]*x[3], x[0]*x[1]*x[3], x[0]*x[1]*x[2]]]

res = minimize(f, [1, 5, 5, 1], jac=grad, bounds=[(1, 5)] * 4,
               constraints=[NonlinearConstraint(cons, [40, 25], [40, np.inf], jac=cons_jac)])
print(res.x, res.fun, res.message)
  • Arguments: fun, x0, args, jac, hess, bounds, constraints, tol, callback, and options, as in scipy.
  • Constraints: SLSQP-style dicts, NonlinearConstraint, and LinearConstraint. The package's own classes and scipy's are both accepted. Jacobians may be dense or sparse.
  • Derivatives are required: the gradient (jac) and each nonlinear constraint's Jacobian. Unlike scipy, there are no finite differences.
  • Exact Hessian: hess selects the exact Hessian of the Lagrangian. The options inertia_control, direct_qp, and direct_least_squares use QDLDL, or MUMPS with 'linear_solver': 'mumps' in an extension built with it (pixi run build-python-mumps; see Sparse solver).
  • Options: options takes any setting in this guide, by name ({'ktol': 1e-8, 'hessian_mode': 'sr1'}), by Fortran reference ('linesearch%filter%delta'), or as the dict returned by the options dialog.
  • Step limits: max_step gives the largest change of each variable in one major iteration, as one value or an array (see Step limits).
  • Warm start: lambda0 gives the starting multipliers, so minimize(..., x0=res.x, lambda0=res.v) restarts from a previous result.
  • Printed output: output_file writes the solver's printed output to a file instead of the process's standard output, which a Jupyter notebook doesn't show.
  • Diagnostics: with options={'diagnostic_level': 1} (or more), the result's diagnostics is a dict with the diagnosis (its indices are 0-based). diagnostics_file writes the history of the iterations to a file, from level 2.
  • Result: an OptimizeResult, which also has the multipliers, the KKT and feasibility errors, and the counts.
  • Least squares: least_squares(fun, x0, jac) minimizes \( \tfrac12 \sum r_i(x)^2 \) for residuals fun with the Jacobian jac, with the same bounds, constraints, and options (see Least-squares problems).

Step limits problem%set_max_step

When the variables have different units or sensitivities (a velocity change in km/s next to an epoch in days), you often know how far each can move before the problem's linearization stops being useful. set_max_step gives the solver that: a limit on the change of each variable in one major iteration.

call problem%set_bounds(x_lb, x_ub, c_lb, c_ub)
call problem%set_max_step([0.1_wp, 0.1_wp, sqpopt_infinity, 5.0_wp])   ! (no limit on the third variable)

The limits are bounds on the steps the solver computes: the QP subproblem is solved with \( |p_j| \le \) max_step(j) next to the variables' own bounds, so its step is the best one within the limits, not a longer one cut short. The second-order correction, the restoration steps, and the trust region respect them too. They are in addition to the solver's own cap on the length of the whole step (qp_solver%max_step, which treats the variables alike and adapts as the solve goes). The printed header reports how many variables are limited.

Limits usually cost iterations (the Rosenbrock function on the unit disk of the Performance page takes 39 steps with limits of 0.2 and 0.05, instead of 12), so set them where they prevent steps into regions where the functions can't be evaluated or the model is meaningless, not everywhere. With the Python bindings: minimize(..., max_step=...).

Hessian approximation sqpopt_hessian_type

A limited-memory quasi-Newton approximation (never a dense n×n matrix), or the user's exact sparse Hessian (sqpopt_hessian_exact, see Exact Hessian). solve() always re-initializes it from options%lbfgs_memory and options%hessian_mode. Apart from those two options fields and options%inertia_control, only damping, shift_min, and shift_max are configurable, on a sqpopt_hessian_type you construct yourself.

With the exact Hessian, the QP subproblems use \( H + \delta I \). The shift \( \delta \) starts at 0. Whenever a QP subproblem finds negative curvature (it was nonconvex), fails, or doesn't give a descent direction, \( \delta \) is increased tenfold (starting from shift_min times the Hessian's largest element) and the QP is re-solved; it also increases after a failed step or a run of very short ones. After each good step it is divided by 3, down to 0. This is a simple form of the inertia correction used by IPOPT and Uno, without a factorization.

Multipliers after a large shift. The exact Hessian is evaluated with the multipliers, and those come from the QP, where they satisfy \( g + (H + \delta I)p = J^T\lambda \). When the shift's term \( \delta p \) is larger than the gradient (\( \delta\lVert p\rVert_\infty \ge \max(1, \lVert g\rVert_\infty) \)), the multipliers mostly balance the shift, and can be orders of magnitude too large. The next Hessian would then be more indefinite and need a larger shift still. So after such a step, the multipliers are replaced by their least-squares estimate at the new point, \( \min_\lambda \lVert g - J^T\lambda \rVert \) over the active constraints and the variables not at a bound, which doesn't depend on the shift. (On a hanging-chain problem, without this, the multipliers grew to \( 10^{13} \) and the solver stopped as stalled far from the solution.) This applies with and without inertia control.

Inertia control

The tests above (for the exact Hessian) only see negative curvature along the directions that the QP solver happens to explore, each correction costs a whole QP solve, and tenfold steps overshoot the shift that is needed. With options%inertia_control = .true., the shift is instead found from a sparse \( LDL^T \) factorization of the KKT matrix

\[ K = \begin{bmatrix} H + \delta I & J_a^T \\ J_a & 0 \end{bmatrix} \]

where \( J_a \) holds the Jacobian rows of the QP's working set, in the variables that are not at a bound. The numbers of positive and negative pivots of the factorization (the inertia of \( K \)) tell exactly whether \( H + \delta I \) has negative curvature on the null space of the working set, which is what makes the QP nonconvex there. Each major iteration:

  1. Before the QP is solved, \( K \) is factored for the working set that the QP starts from (the one the previous QP ended with). If it has negative curvature, \( \delta \) is raised and \( K \) refactored until none is left: first to shift_min times the Hessian's largest element (or a third of the last shift that was needed, if that is larger), then 8 times as much at each attempt, much as IPOPT does. Each attempt costs a factorization, not a QP solve.
  2. After the QP is solved, the same test is made for the working set it ended with, if that is a different one. Only if it fails is \( \delta \) raised further and the QP re-solved. (With the trust region, this second test is not made.)

The shift starts from 0 again at every iteration, so it disappears as soon as it isn't needed, and the Newton steps near a solution are not damped. A QP that fails or doesn't give a descent direction still raises the shift, as does a failed step or a run of very short ones (those increases are carried over, and decay as above). The QP subproblems themselves are solved by the same solvers as before.

SR1. The limited-memory SR1 matrix can be indefinite too, and without inertia control nothing corrects it. It is a multiple of the identity plus a matrix of low rank, so the same test applies: the sparse part of \( K \) is factored, and the low-rank part is accounted for with a small dense matrix (one solve per stored pair). On the Hock–Schittkowski problems, SR1 then solves 274 problems and fails on 4, instead of 244 and 30, with less than a quarter of the function evaluations (10,454 instead of 44,905), the same with both solvers. The shift isn't carried over between iterations with SR1.

It is used with sqpopt_hessian_exact and sqpopt_hessian_sr1 (the BFGS matrix is positive definite, and needs no correction). The factorizations are those of options%linear_solver (see Sparse solver). With SR1 both solvers give the same results; with the exact Hessian, MUMPS is the better one, since QDLDL can't tell the inertia of a Hessian with zeros on its diagonal, and then shifts it more than needed. MUMPS runs on one thread unless options%factorization_threads says otherwise (see Threads). results%n_factorizations counts the factorizations. On the Hock–Schittkowski problems, the exact Hessian with it solves 4 more problems than without it with MUMPS (274 instead of 270), with 16% fewer function evaluations, and 3 more with QDLDL, but with 22% more evaluations (see Performance). With options%direct_qp, the factorizations are also used to solve the QP (see Direct method).

The unconstrained step qp_solver%unconstrained_step

The L-BFGS matrix \( H \) is positive definite, so the QP's objective alone has the minimizer \( p = -H^{-1} g \), which the two-loop recursion gives at the cost of a few vector operations per stored pair. Before a QP solver is run, that step is tried: if \( x + p \) is within the bounds and the linearized constraints, it is the solution of the QP, with zero multipliers. So a problem without constraints is solved as a plain L-BFGS method wherever its bounds aren't active, and an iteration of a constrained problem at which nothing is active costs no QP solve either. When the step isn't feasible, the QP solver runs as before, and the attempt has cost one product.

This matters for large problems. The active-set solvers handle a QP with every variable free too, but the sparse one does it by conjugate gradients on a matrix of the order of the problem. With 1,000 variables, the chained Rosenbrock function (4,946 iterations) takes 7.8 seconds with the step and 78 without it, and the same iterations. results%n_unconstrained_qp counts the QPs solved this way. The step isn't used with the exact Hessian or SR1 (which can be indefinite, and have no such inverse), nor in an elastic re-solve. On the Hock–Schittkowski problems it changes little: 9,067 fc calls instead of 9,173, with the same problems solved.

Both active-set solvers enforce the linearized constraints and bounds exactly, and share the same robustness features:

  • Elastic mode. Each linearized constraint violated at p = 0 gets a nonnegative slack with an \( \ell_1 \) penalty (SNOPT's elastic mode). This gives a feasible starting point with no separate phase-1 problem. If slacks remain positive at the solution, the penalty weight is raised (up to elastic_weight_max). If they are still positive then, the linearized constraints are inconsistent: the QP returns sqpopt_infeasible, and the major iteration takes a feasibility-restoration step instead.
  • Dependent constraints. Rows join the working set only if they are linearly independent of it. The sparse solver picks its initial basis and working set with one rank-revealing LUSOL factorization, preferring to keep equality constraints, then bounds, then inequalities, so duplicated or dependent constraints are handled.
  • Negative curvature. Directions of zero or negative curvature (an indefinite SR1 Hessian, or along an elastic slack) are followed to the nearest blocking constraint rather than producing a huge Newton step. All tolerances are relative to the problem's scale.
  • Crash and warm starts. Iterations start from the minimum-norm step satisfying an initial working-set guess, rather than from p = 0, so only the constraints the guess leaves violated need elastic slacks. The guess is the previous QP's final working set (warm_start, on by default; near a solution the active set settles and the QP finishes in one or two iterations), or else the equality constraints and fixed variables.
  • Tested. Both are checked against the KKT conditions on thousands of random convex, nonconvex, degenerate, and infeasible QPs (test/test_qp_fuzz.f90).

Direct method options%direct_qp

On large problems, nearly all of a solve's time is in the active-set QP solvers: each of their iterations changes one constraint and solves with the reduced Hessian. With options%direct_qp = .true., each QP is first tried directly. For a given working set, the QP is an equality-constrained one, and its solution is one linear solve with the KKT matrix

\[ \begin{bmatrix} H & J_a^T \\ J_a & 0 \end{bmatrix} \begin{bmatrix} p \\ -\lambda \end{bmatrix} = \begin{bmatrix} -g \\ b_a - c_a \end{bmatrix} \]

which is factored by the sparse solver of options%linear_solver (the same factorization as the inertia control's, which is reused). The method is a primal-dual active-set method:

  1. Start from the working set of the previous QP (or, for the first one, the equality constraints and fixed variables). Near a solution of the nonlinear problem that is already the right one.
  2. Factor and solve. If the step satisfies every row and bound outside the working set, and every multiplier has the right sign, it is the QP's solution.
  3. Otherwise add every row and bound the step violates, drop every one whose multiplier has the wrong sign, and go back to 2.

If that hasn't found the solution after qp_solver%direct_max_changes changes, the QP is solved by the active-set solver as usual, so nothing is lost but the factorizations. A step is only accepted if it satisfies the QP's optimality conditions, so the result is the same QP solution either way. Two refinements keep it going where it would otherwise give up:

  • A nonconvex face. With inertia control, the Hessian's shift is raised until the face is convex, and the method continues.
  • A singular KKT matrix (adding every violated bound at once can leave a row with no free variable): the face is factored again with a small regularization, which gives the over-determined rows large multipliers, so the bounds responsible are dropped at the next change. (If the step of a regularized face fails only because its rows aren't quite satisfied, it is solved once more with a much smaller regularization.)

Which Hessian. It works with every Hessian mode:

  • Exact Hessian (use it with inertia_control): the sparse Hessian goes into the KKT matrix as it is. This is where it pays most: in the large-problem benchmark, every QP was solved directly, and the solves were 2 to 200 times faster than with the active-set QP, the more so the larger the problem.
  • L-BFGS and SR1: the quasi-Newton matrix is a multiple of the identity plus a matrix of low rank, which is handled by the Sherman–Morrison–Woodbury formula. That costs two more solves per stored pair for each factorization, and work that grows with the square of the number of pairs. So with direct_qp the automatic memory (options%lbfgs_memory = 0) is 10 pairs, not up to 100. A larger memory can be set, but it didn't pay in the large-problem benchmark.

It is used by the line searches and by the trust region, but not for the feasibility QPs of a restoration phase, nor for an elastic re-solve. results%n_direct_qp and results%n_qp_solves tell how many QPs it solved, and results%time_factorization what the factorizations cost. At print_level = 3, each QP's line says whether it was solved directly, and if not, why the direct method gave up.

Sparse solver options%linear_solver

The inertia control, the direct method, and direct least squares factor symmetric matrices with one of three solvers:

  • QDLDL (sqpopt_linear_solver_qdldl, the default): a Fortran port of the \( LDL^T \) solver of the OSQP QP solver (qdldl-fortran), which FPM fetches, so it is always available, in any precision. It orders the matrix for sparsity (approximate minimum degree, with dense rows last and each constraint's row after its variables), and factors it without pivoting, on one thread, with very little overhead.
  • MUMPS (sqpopt_linear_solver_mumps): a multifrontal solver with pivoting and threads (options%factorization_threads), in a library built with it (see Installation); invalid input otherwise.
  • Dense (sqpopt_linear_solver_dense): forms the matrix as a dense array, of order \( n + m \), and factors it with pivoting (LU), counting its inertia exactly (as MUMPS does, also with zeros on the Hessian's diagonal) from SQPOPT's own dense routines. Each factorization costs \( O((n+m)^3) \) operations and \( 2(n+m)^2 \) numbers of memory, so it is only for small problems: up to a few hundred variables and constraints. Above an order of 2,000 it refuses to start, and the three options then fall back on the matrix-free methods. Always available; opt-in only (see Options that form dense matrices).
  • LAPACK (sqpopt_linear_solver_lapack): the same dense matrix, factored by LAPACK's DSYTRF (the Bunch–Kaufman \( LDL^T \) factorization, which gives the inertia too) instead of SQPOPT's own routines: 20 to 60 times faster than the dense solver near its limit, and on the HS problems as good as MUMPS with every Hessian. The same size limit and memory; opt-in only, in a library built with LAPACK (see Installation).

QDLDL is the default in every build; the others are used only when you choose them. The log's header names the solver in use.

Which one to choose.

  • QDLDL for problems whose coupling is banded or along a chain (discretized time, chains of constraints), for the quasi-Newton Hessians (BFGS and SR1), and for direct least squares. Its matrices there are exact for a solver without pivoting, both solvers give the same iterates, and QDLDL's factorizations are several times faster.
  • MUMPS, or for a small problem dense, for the exact Hessian with inertia control: with a Hessian that has zeros on its diagonal, a solver without pivoting can't tell the inertia (it would need the 2-by-2 pivots MUMPS has), so QDLDL reports negative curvature rather than miss it, and the shift is larger than needed, which costs evaluations. The dense solver gives MUMPS's results there, at QDLDL's speed and without MUMPS, but only while the problem is small; LAPACK's, if your build has it, does as well with every Hessian, and stays fast up to the size limit.
  • MUMPS for problems coupled in two or three dimensions (a PDE on a grid, a mesh), whose factors have large dense blocks: there its multifrontal method, and its threads, are many times faster. But its first factorization of a KKT matrix, which includes its analysis, can cost much more than QDLDL's, so for a solve that factors only a few times, try both.

Threads options%factorization_threads

Direct least squares options%direct_least_squares

The Gauss-Newton restoration step and the second-order correction both need the minimum-norm solution of \( J_S\,d = r \) for some rows of the Jacobian. They use the iterative solver LSQR, and take no step if it stops at its iteration limit. With options%direct_least_squares = .true., the solution comes from one sparse factorization of \( \begin{bmatrix} I & J_S^T \\ J_S & -\epsilon I \end{bmatrix} \) instead (with a small \( \epsilon \), so that dependent rows are no problem), with any Hessian mode.

It pays when the problem is large and the rows are coupled, because LSQR then needs a number of iterations that grows with the problem:

  • Second-order corrections: on a chain of coupled circle constraints (circles in the large-problem benchmark), a solve with 3 corrections took 88.7 s with LSQR and 0.16 s with direct least squares at 100,000 variables (0.59 s and 0.011 s at 10,000; with MUMPS as the sparse solver, 1.1 s and 0.08 s).
  • Restoration steps: on a chain of hyperbola constraints with 10,000 variables (hyperbolas there), the 9 Gauss-Newton restoration steps took 2.3 s with LSQR and 0.02 s directly (though that problem's total time is dominated by the QPs that find the linearization inconsistent).

On small problems it changes little, and not always for the better: on the Hock–Schittkowski problems the default options solve 278 problems with it and fail on one (TP106, where a more accurate correction leads to a slow crawl), against 281 and none without it. So it is off by default: turn it on for large problems that take corrections or restoration steps (results%n_soc, results%n_restoration_steps) and spend their time outside the QP and the user functions.

Feasibility restoration options%restoration_mode

When the filter or funnel line search, or the trust region, finds no acceptable step at an infeasible point, the solver enters a feasibility restoration phase (sqpopt_restoration_phase, the default), as in filter-SQP methods and the Uno solver:

  • The current point is added to the filter (or the funnel is tightened toward it), so the iterations can't cycle back to it.
  • Each iteration of the phase solves a feasibility QP with the regular QP solvers: its objective is a proximal term toward the point where the phase started, and it enforces the linearized constraints or, if they are inconsistent, minimizes their \( \ell_1 \) violation (the QP's elastic mode). A backtracking search then requires a decrease of the \( \ell_1 \) violation (an Armijo test against the decrease the linearization predicts). If this fails, a Gauss-Newton step on the violation is taken instead.
  • The phase ends once the violation is below restoration_exit_factor times its value where the phase started and the point is acceptable to the filter or funnel, when the point is feasible, or after restoration_max_iter iterations. The multipliers are kept from before the phase.

An inconsistent QP (linearized constraints that can't be satisfied) is still handled with a single Gauss-Newton step on the violation, falling back to the QP's elastic step, which also accounts for the objective. With sqpopt_restoration_gauss_newton, that single step is also used when the filter or funnel line search fails, and the trust region takes no restoration step at all. Before a point is reported as infeasible (a point where the violation can't be decreased to first order), the solver also probes for a second-order decrease of the violation, which escapes, for example, symmetry planes of the problem.

Problems with more equality constraints than variables have an inconsistent QP at every iteration, so they are solved by these Gauss-Newton steps alone: SQPOPT then acts as a least-squares solver for the constraints. The cap on the step's length (qp_solver%max_step) adapts after these steps as it does after a line search: a full step that the cap cut short doubles it, and a shortened one halves it. A solution far from the starting point is then reached in a few iterations, not by steps of the cap's length.

If the equations can't all hold (a data-fitting problem written as one equation per data point), the solve ends as sqpopt_infeasible at best, at a least-squares solution of the constraints (of the scaled constraints, with the automatic scaling, which weights them differently from the original ones). Where the Jacobian is nearly rank deficient, the Gauss-Newton step finds no decrease, and the solve ends as a line-search failure or at the iteration limit instead. Give such a problem to the least-squares interface, which solves it as an ordinary problem with far fewer evaluations.

  • PSQP: another SQP code, originally by Ladislav Lukšan

Other solvers

  • Uno: a modular solver for nonlinearly constrained optimization by Charlie Vanaret and Sven Leyffer (C++, MIT license). It builds SQP, interior-point, and other methods from interchangeable parts. SQPOPT's funnel method and restoration phase follow it.
  • IPOPT: an interior-point solver for large-scale nonlinear optimization by Andreas Wächter and Lorenz Biegler (C++, EPL license). SQPOPT takes from it the rules of its filter line search, its gradient-based scaling, the acceptable-level stopping test, and the shift search of its inertia control.

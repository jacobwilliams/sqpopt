Modern Fortran SQP OPTimizer

SQPOPT

A modular, extensible Sequential Quadratic Programming solver for large-scale, sparse, nonlinearly constrained optimization problems.

Get started Options reference API docs

SQPOPT solves problems of the form

\[ \begin{aligned} \min_{x}\quad & f(x) \\ \text{subject to}\quad & c_{lb} \le c(x) \le c_{ub} && \text{(nonlinear, possibly two-sided, constraints)}\\ & x_{lb} \le x \le x_{ub} && \text{(variable bounds)} \end{aligned} \]

where an equality constraint is written as c_lb(i) = c_ub(i). The objective, the constraints, and their first derivatives are supplied as callbacks. The constraint Jacobian is stored in sparse coordinate (COO) format, and the Hessian of the Lagrangian is approximated by a matrix-free, limited-memory quasi-Newton operator. No dense n×n or m×n array is ever formed, so the library scales to large, sparse problems.

SQP method

Nonlinear objective, nonlinear equality and inequality constraints, and bounds.

Sparse throughout

COO constraint Jacobian, matrix-free L-BFGS / L-SR1 Hessian, sparse LU-based QP solver.

Modular

Problem, options, Hessian, QP solver, line search and convergence are separate modules you can swap independently.

Robust globalization

Filter line search (default), funnel, Armijo, watchdog, or exact line search, or a trust region; second-order corrections.

Selectable precision

Single, double, or quadruple precision reals.

FPM-native

Add it to any project as a Fortran Package Manager dependency.

Work in progress. The API is still evolving. The API reference generated by FORD from the source code always matches the current code.

Installation

SQPOPT is built with the Fortran Package Manager. To use it in your own project, add it to your fpm.toml:

[dependencies]
sqpopt = { git = "https://github.com/jacobwilliams/sqpopt" }

FPM fetches and builds its dependencies for you. SQPOPT uses double precision (real64) unless you choose another kind with a preprocessor flag:

fpm build --profile release --flag "-DREAL32"    # single precision
fpm build --profile release --flag "-DREAL128"   # quadruple precision

The working kind is exported as sqpopt_module_wp from sqpopt_kinds. The examples below import it as wp.

Quick start

You need three objects: a problem (sizes, bounds, sparsity, and callbacks), some options, and the solver.

use sqpopt_module,         only: sqpopt_type
use sqpopt_problem_module, only: sqpopt_problem_type
use sqpopt_options_module, only: sqpopt_options_type
use sqpopt_kinds,          only: wp => sqpopt_module_wp

type(sqpopt_type)         :: solver
type(sqpopt_problem_type) :: problem
type(sqpopt_options_type) :: options
real(wp) :: x(n), lambda(m)
integer  :: istat

call problem%set_problem_size(n, m_eq, m_ineq)
call problem%set_bounds(x_lb, x_ub, c_lb, c_ub)
call problem%set_jacobian_sparsity(nnz, irow, icol)          ! fixed sparsity pattern
call problem%set_functions(fc=fc, gjac=gjac)                 ! optionally also data=...

call solver%initialize(problem=problem, options=options)
call solver%solve(x0, istat)            ! optionally also lambda0=...
call solver%get_solution(x, lambda)     ! optionally also z (bound multipliers)
print *, solver%status_message()        ! e.g. 'converged successfully'

Before iterating, solve checks the problem definition and every option. If anything is wrong it returns istat = sqpopt_invalid_input, and status_message() gives the reason. It also moves x0 inside the variable bounds, so your functions are never evaluated outside the bounds.

Every call to solve starts from the configuration given to initialize. No state (penalty parameter, filter, Hessian, …) carries over from a previous solve.

User functions

The problem is defined by two routines: fc evaluates the objective \( f(x) \) and the constraints \( c(x) \) together, and gjac evaluates the objective gradient and the constraint Jacobian together. (They usually share intermediate results, which each routine can compute once.)

subroutine fc(x, f, c, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp),               intent(out)   :: f
    real(wp), dimension(:), intent(out)   :: c        ! dimension(m); m may be 0
    integer,                intent(inout) :: status   ! 0 on entry
    class(*), optional,     intent(inout) :: data
    f = ...
    c = ...
end subroutine fc

subroutine gjac(x, g, jac_val, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp), dimension(:), intent(out)   :: g        ! dimension(n)
    real(wp), dimension(:), intent(out)   :: jac_val  ! dimension(nnz); nnz may be 0
    integer,                intent(inout) :: status   ! 0 on entry
    class(*), optional,     intent(inout) :: data
    g = ...
    jac_val = ...
end subroutine gjac

The Jacobian values must be in the order of the irow/icol pattern given to set_jacobian_sparsity. The solver keeps a small cache of recent evaluations, so asking for c at a point where it just evaluated f (or for the Jacobian where it just evaluated the gradient) doesn't call your routine again.

status
Leave it 0 on success. Set it > 0 if the function can't be evaluated at x (for example, a domain error). The solver treats that point like one where the function returned NaN (all of its outputs, e.g. both f and c), and backs off from it. Set it < 0 to stop the solver (sqpopt_user_requested_stop). No user function is called again after that.
data
The object passed as set_functions(..., data=my_data) (absent if none was given). Use it to pass any context to the functions without module variables, and access it with select type. It is pointed to, not copied, so the caller's object needs the target attribute, and any changes the functions make to it are seen by the caller. It is also passed to the report callback.

Progress callback

Pass report=my_report to initialize to be called once per major iteration. Set user_stop = .true. to stop after the current iteration. All values are for the original (unscaled) problem.

subroutine my_report(iter, x, f, c, lambda, user_stop, data)
    integer,                intent(in)    :: iter       ! major iteration (starts at 1)
    real(wp), dimension(:), intent(in)    :: x, c, lambda
    real(wp),               intent(in)    :: f
    logical,                intent(out)   :: user_stop
    class(*), optional,     intent(inout) :: data
    user_stop = .false.
end subroutine my_report

Worked example: Hock–Schittkowski 71

\[ \begin{aligned} \min_{x}\quad & x_1 x_4 (x_1 + x_2 + x_3) + x_3 \\ \text{subject to}\quad & x_1^2 + x_2^2 + x_3^2 + x_4^2 = 40 \\ & x_1 x_2 x_3 x_4 \ge 25 \\ & 1 \le x_i \le 5 \end{aligned} \]

Starting from \( x_0 = (1, 5, 5, 1) \), the solution is \( x^* \approx (1,\ 4.743,\ 3.821,\ 1.379) \) with \( f^* \approx 17.014 \). Both constraints are active there.

program hs71

use sqpopt_module,         only: sqpopt_type
use sqpopt_problem_module, only: sqpopt_problem_type
use sqpopt_options_module, only: sqpopt_options_type
use sqpopt_kinds,          only: wp => sqpopt_module_wp

implicit none

real(wp), parameter :: big = 1.0e20_wp   ! "no bound"
type(sqpopt_type)         :: solver
type(sqpopt_problem_type) :: problem
type(sqpopt_options_type) :: options
real(wp) :: x(4), lambda(2)
integer  :: istat

! equality constraint (index 1) first, then the inequality (index 2)
call problem%set_problem_size(n=4, m_eq=1, m_ineq=1)
call problem%set_bounds(x_lb=[1.0_wp,1.0_wp,1.0_wp,1.0_wp], x_ub=[5.0_wp,5.0_wp,5.0_wp,5.0_wp], &
                        c_lb=[40.0_wp, 25.0_wp], c_ub=[40.0_wp, big])
call problem%set_jacobian_sparsity(nnz=8, irow=[1,1,1,1,2,2,2,2], icol=[1,2,3,4,1,2,3,4])
call problem%set_functions(fc=fc, gjac=gjac)

options%print_level = 1

call solver%initialize(problem=problem, options=options)
call solver%solve([1.0_wp, 5.0_wp, 5.0_wp, 1.0_wp], istat)
call solver%get_solution(x, lambda)
print *, solver%status_message()
print *, 'x = ', x

contains

    subroutine fc(x, f, c, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp),               intent(out)   :: f
    real(wp), dimension(:), intent(out)   :: c
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    f = x(1)*x(4)*(x(1)+x(2)+x(3)) + x(3)
    c = [sum(x**2), product(x)]
    end subroutine fc

    subroutine gjac(x, g, jac_val, status, data)
    real(wp), dimension(:), intent(in)    :: x
    real(wp), dimension(:), intent(out)   :: g
    real(wp), dimension(:), intent(out)   :: jac_val
    integer,                intent(inout) :: status
    class(*), optional,     intent(inout) :: data
    g = [x(4)*(2.0_wp*x(1)+x(2)+x(3)), x(1)*x(4), x(1)*x(4) + 1.0_wp, x(1)*(x(1)+x(2)+x(3))]
    jac_val(1:4) = 2.0_wp*x                                   ! row 1: d(sum x^2)/dx
    jac_val(5:8) = [x(2)*x(3)*x(4), x(1)*x(3)*x(4), &         ! row 2: d(prod x)/dx
                    x(1)*x(2)*x(4), x(1)*x(2)*x(3)]
    end subroutine gjac

end program hs71

For more complete examples, see test/test_basic.f90, test/test_hs71.f90 (which solves this problem eleven different ways), and test/test_medium.f90.

Results

After a solve, solver%get_results(results) returns a sqpopt_results_type (from sqpopt_types_module):

fielddescription
istat, messagestatus code and its description
iterationsnumber of major iterations performed
n_eval_fc, n_eval_gjacnumber of calls of the user functions fc and gjac
timewall-clock time of the solve (seconds)
x, f, cfinal point, and the objective and constraint values there
lambdaconstraint multipliers, dimension(m)
zvariable-bound multipliers, dimension(n) (zero for a variable not at a bound)
kkt_errorKKT (stationarity/complementarity) error, of the scaled problem used by the convergence test
feasibility_errorlargest violation of a constraint or variable bound

All of these are for the original problem, even when automatic scaling is on. The Lagrangian is \( L = f - \lambda^T c - z^T x \), so a multiplier is \( \ge 0 \) at a lower bound and \( \le 0 \) at an upper bound.

If no acceptable step can be found along a search direction, no step is taken: the point is never moved to one that makes the merit function worse. The Hessian approximation is reset instead, so the next iteration tries a different direction.

How configuration works

solver%initialize accepts one instance of each sub-component. All are optional, and defaults are used for anything you leave out:

call solver%initialize(problem=..., options=..., hessian=..., qp_solver=..., &
                       linesearch=..., trust_region=..., report=...)
sqpopt_typethe solver
sqpopt_problem_typesizes, bounds, callbacks sqpopt_options_typecommon settings & mode selectors sqpopt_hessian_typequasi-Newton Hessian sqpopt_qp_solver_typeQP subproblem sqpopt_linesearch_typeline search & merit sqpopt_trust_region_typetrust region (opt-in)

sqpopt_options_type holds the most commonly tuned settings, including the ones that select an algorithm. The other types expose further tuning parameters for each algorithm. You set those by constructing the component yourself and passing it in:

type(sqpopt_qp_solver_type)  :: qp_solver
type(sqpopt_linesearch_type) :: linesearch

qp_solver%max_step             = 5.0_wp
qp_solver%sparse_qp%lsqr_atol  = 5.0e-10_wp
linesearch%major_step_limit    = 1.0_wp

call solver%initialize(problem=problem, options=options, qp_solver=qp_solver, linesearch=linesearch)

Mode selectors are copied down on every solve. At the start of every solve(), these options fields overwrite the corresponding sub-component fields:

options%…overwrites
hessian_mode, lbfgs_memoryhessian (re-initialized)
qp_solver_modeqp_solver%mode
linesearch_modelinesearch%mode
merit_modelinesearch%merit_mode
penalty_updatelinesearch%penalty_update

So set these through options. Everything else in the tables below (tolerances, step limits, and so on) has no options field and must be set on the sub-component directly.

Every setting of every component is checked when solve starts. An invalid value gives sqpopt_invalid_input, and status_message() names the setting.

Hessian approximation sqpopt_hessian_type

A limited-memory quasi-Newton approximation (never a dense n×n matrix). solve() always re-initializes it from options%lbfgs_memory and options%hessian_mode. Apart from those two options fields, only damping is configurable, on a sqpopt_hessian_type you construct yourself.

optiondefaultdescription
options%hessian_modesqpopt_hessian_bfgssqpopt_hessian_bfgs (limited-memory Powell-damped BFGS), sqpopt_hessian_sr1 (limited-memory symmetric rank-1), or sqpopt_hessian_exact (not yet implemented; falls back to BFGS)
options%lbfgs_memory10number of (s,y) vector pairs retained, independent of the problem size n
damping.true.Powell's damped BFGS update: when \( s^Ty < 0.2\,s^TBs \), y is blended with Bs so the update keeps B positive definite while still using the new curvature information. If .false., such updates are skipped instead.

QP modes options%qp_solver_mode

valuedescription
sqpopt_qp_auto defaultsqpopt_qp_dense if n <= auto_dense_max_n, else sqpopt_qp_reduced_hessian
sqpopt_qp_densedense active-set QP (Householder QR null space, Cholesky factorization of the reduced Hessian). It forms O(n²)/O(mn) dense arrays on each call, so it is best for small-to-moderate problems.
sqpopt_qp_reduced_hessiansparse active-set QP (SQOPT-style basis partition of the working set with sparse LUSOL factors, conjugate gradients on the reduced Hessian, active bounds handled by fixing variables). It never forms a dense array, so it scales to larger problems.

Both active-set solvers enforce the linearized constraints and bounds exactly, and share the same robustness features:

  • Elastic mode. Each linearized constraint violated at p = 0 gets a nonnegative slack with an \( \ell_1 \) penalty (SNOPT's elastic mode). This gives a feasible starting point with no separate phase-1 problem. If slacks remain positive at the solution, the penalty weight is raised (up to elastic_weight_max). If they are still positive then, the linearized constraints are inconsistent: the QP returns sqpopt_infeasible, and the major iteration takes a feasibility-restoration step instead.
  • Dependent constraints. Rows join the working set only if they are linearly independent of it. The sparse solver picks its initial basis and working set with one rank-revealing LUSOL factorization, preferring to keep equality constraints, then bounds, then inequalities, so duplicated or dependent constraints are handled.
  • Negative curvature. Directions of zero or negative curvature (an indefinite SR1 Hessian, or along an elastic slack) are followed to the nearest blocking constraint rather than producing a huge Newton step. All tolerances are relative to the problem's scale.
  • Crash and warm starts. Iterations start from the minimum-norm step satisfying an initial working-set guess, rather than from p = 0, so only the constraints the guess leaves violated need elastic slacks. The guess is the previous QP's final working set (warm_start, on by default; near a solution the active set settles and the QP finishes in one or two iterations), or else the equality constraints and fixed variables.
  • Tested. Both are checked against the KKT conditions on thousands of random convex, nonconvex, degenerate, and infeasible QPs (test/test_qp_fuzz.f90).

Line search modes options%linesearch_mode

valuedescription
sqpopt_linesearch_filter defaultfilter line search (Fletcher & Leyffer's filter, with the globally convergent line-search rules of Wächter & Biegler, as in IPOPT). No merit function or penalty parameter: a trial point is judged by its (violation, objective) pair, which must not be dominated by the filter. A switching condition decides whether the step must reduce the objective (Armijo) or may trade it for feasibility, and only the latter steps enlarge the filter. If no acceptable step is found, a feasibility-restoration step is taken. Ignores merit_mode and penalty.
sqpopt_linesearch_funnelthe funnel method of Kiessling, Leyffer & Vanaret (as in the Uno solver). Like the filter, no merit function or penalty parameter, but the filter's list of points is replaced by a single number: the funnel width, a bound on the violation that shrinks as the iterations progress. A trial point must be inside the funnel. If the switching condition holds, it must reduce the objective (Armijo, "f-type"); otherwise it must be sufficiently inside the funnel ("h-type"), which then shrinks. If no acceptable step is found, the funnel is tightened toward the current violation and a feasibility-restoration step is taken. Ignores merit_mode, penalty, and nonmonotone_len.
sqpopt_linesearch_armijostandard backtracking line search with an Armijo-type sufficient-decrease test on the merit function (the default in slsqp)
sqpopt_linesearch_exact(approximately) minimizes the merit function along the search direction using the derivative-free fmin routine
sqpopt_linesearch_watchdogPowell's watchdog technique: tracks the best point found so far and, for a short window after a genuine improvement, relaxes the sufficient-decrease test (accepting the full step outright) rather than stalling near a curved constraint boundary (the Maratos effect). If the window is used up without a new best point, it backtracks to the best point and disables relaxed acceptance for watchdog_cooldown_len iterations.

Merit functions options%merit_mode

valuedescription
sqpopt_merit_l1 defaultnon-smooth \( \ell_1 \) exact penalty function (as in slsqp)
sqpopt_merit_augmented_lagrangiansmooth augmented Lagrangian merit function (Gill, Murray, Saunders & Wright; the merit function used in NPSOL and, in spirit, SNOPT). It is twice continuously differentiable, which helps avoid the Maratos effect.

Penalty updates options%penalty_update

valuedescription
sqpopt_penalty_multipliers defaultkeep the penalty above the multiplier estimates, \( \mu \ge \lVert\lambda\rVert_\infty + 1 \) (Han/Powell, as in slsqp). It never decreases, so it can grow very large at degenerate points.
sqpopt_penalty_modeleach merit function's principled rule.
  • sqpopt_merit_l1: Byrd–Nocedal model reduction. The penalty only increases as needed for the step's predicted merit reduction to credit a fraction penalty_rho of its linearized violation reduction.
  • sqpopt_merit_augmented_lagrangian: Gill–Murray–Saunders–Wright. The line search moves the multipliers (toward the QP's) and the slacks (toward the QP's linearized constraint values) along with the variables. The penalty is set just large enough for the merit's slope to be at most \( -\tfrac12 p^THp \), and it can also decrease (a limited number of times).

Second-order correction. In every line search, and in the trust region, when the first (full) trial step is rejected without reducing the constraint violation (the signature of the Maratos effect near curved constraints), a second-order-corrected step is tried before backtracking. This is a minimum-norm correction for the true constraint values at the trial point, using the current Jacobian, kept within the bounds. See sqpopt_soc_module.

Trust-region globalization sqpopt_trust_region_type

An opt-in alternative to the line search, disabled by default. Instead of solving the QP once and searching for a step length \( \alpha \) along the resulting \( p \), the QP is re-solved as needed with a shrinking trust-region radius until a step is accepted or the retries are exhausted. The radius is enforced by temporarily tightening the variable bounds passed to whichever qp_solver_mode is selected, so it works with every QP solver.

Set as trust_region%<name>.

optiondefaultdescription
enabled.false.if .true., use trust-region radius management instead of the line search for every major iteration
radius01.0initial trust-region radius
radius_min1e-8below this, a major iteration's retries give up (no step is taken)
radius_max1e3ceiling on the radius
eta10.1ratio threshold to accept a step (merit-ratio acceptance only; see below)
eta20.75ratio threshold to also grow the radius (merit-ratio acceptance only)
shrink_factor0.5radius *= shrink_factor on a rejected step
expand_factor2.0radius *= expand_factor on an accepted step that used the full radius
max_retries20maximum QP re-solves (with a shrinking radius) per major iteration

When the trust region is enabled, linesearch%mode selects which acceptance test to use, not which line search to run (there is no \( \alpha \) to search for):

  • sqpopt_linesearch_filter uses the same filter acceptance test as the filter line search, with the quadratic model's predicted decrease in the switching condition: a trust-region filter-SQP method in the spirit of Fletcher & Leyffer.
  • sqpopt_linesearch_funnel uses the funnel acceptance test, with the quadratic model's predicted decrease: the trust-region funnel-SQP method of Kiessling, Leyffer & Vanaret (Uno's funnelsqp preset).
  • armijo, exact, and watchdog all use the same classical trust-region SQP ratio test on the merit function selected by merit_mode.

The full design is in plan/TRUST_REGION_PLAN.md.

Dependencies

These are fetched and built automatically by FPM:

  • LSQR: iterative solver for sparse linear systems and least-squares problems
  • lusol: sparse LU factorization (the sparse QP's basis factors and updates, and its rank-revealing basis choice)
  • fmin: derivative-free minimization routine used by the exact line search

Other Fortran SQP solvers

  • SNOPT: large-scale SQP solver by Philip Gill, Walter Murray, and Michael Saunders (commercial)
  • VF13AD: classic SQP method from the HSL Archive
  • SLSQP: originally by Dieter Kraft; one of the optimization methods in SciPy
  • PSQP: another SQP code, originally by Ladislav Lukšan
